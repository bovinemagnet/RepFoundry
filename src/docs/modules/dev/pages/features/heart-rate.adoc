= Heart Rate Monitoring
Paul Snow
0.0.0
:description: Implementation reference for the real-time heart rate monitoring panel in RepFoundry.
:page-aliases: ROOT:features/heart-rate.adoc

IMPORTANT: Heart rate zones are estimated training guidance only — not medical diagnosis or emergency monitoring.

For the user-facing guide to this feature — supported devices, what the zones mean, health profile setup, and the safety features — see xref:ROOT:guide/heart-rate.adoc[].

== Overview

`HeartRatePanelScreen` (`lib/features/heart_rate/presentation/screens/heart_rate_panel_screen.dart`) is reachable from the bottom navigation bar independently of an active cardio or workout session. It shares the `HeartRateService` BLE singleton (`lib/features/cardio/data/heart_rate_service.dart`) with the xref:features/cardio.adoc[Cardio Tracking] feature: if `heartRateServiceProvider` already reports a connection when the panel opens, `syncFromService()` picks it up without reconnecting.

Zone calculation, health profile modelling, and time-in-zone analysis are not implemented in this repository — they are provided by the external `hr_zones` pub package (`hr_zones: ^0.0.2` in `pubspec.yaml`), imported as `package:hr_zones/hr_zones.dart`.

== BLE Connection

Heart rate data is streamed from any device advertising the standard BLE Heart Rate Service (`0x180D`) via `FlutterBlueHeartRateService` (`lib/features/cardio/data/flutter_blue_heart_rate_service.dart`).

[[device-scanning]]
=== Device Scanning

`HeartRateService.scanDevices({Duration timeout})` returns a `Stream<List<DiscoveredHrDevice>>`. `FlutterBlueHeartRateService.scanDevices` is an `async*` method that listens to `FlutterBluePlus.onScanResults` and yields the growing device list as each new device is found, rather than waiting for the whole scan to finish; `scanForDevices` now consumes this stream. `HrDevicePickerDialog._startScan` does `await for` over it and calls `setState` on every emission, so its `_DeviceList` widget can render the list mid-scan as well as once scanning completes. The test double `FakeHeartRateService` (`test/features/cardio/data/fake_heart_rate_service.dart`) exposes `streamScanResults`, `emitScanResult(device)`, and `completeScan()` to drive incremental scans in widget tests.

=== HR Measurement Parsing

The service subscribes to characteristic `0x2A37` and parses both 8-bit and 16-bit heart rate value formats per the BLE specification (`_parseHeartRate`).

=== Connection and Reconnect

* Initial connect (`connectToDevice`) wraps `_connectAndSubscribe` in `retryOnceOnFailure` (`lib/features/cardio/data/reconnect_strategy.dart`) — one retry after a 1-second delay, to absorb the transient Android GATT error 133 that commonly follows a peripheral powering on.
* On an unexpected mid-session disconnect, `_attemptReconnect` runs `ReconnectStrategy.run`, which retries on an exponential backoff schedule (2, 4, 8, 16, 32, then three 60-second delays — eight attempts, a little over four minutes total) before giving up.
* `HrConnectionState` (`connected`, `reconnecting`, `disconnected`) drives UI state via `HeartRatePanelController`, which pauses its wall-clock elapsed-time accumulator (`_pauseClock`) while reconnecting so gaps spent disconnected aren't counted toward session length.
* Calling `disconnect()` sets `_intentionalDisconnect`, which both `_attemptReconnect` and the connection-state listener check before attempting or continuing a reconnect.

== Health Profile

`HealthProfile` (from `package:hr_zones`) captures the data used to personalise zone calculations: `age`, `restingHr`, `measuredMaxHr`, `clinicianMaxHr`, `lactateThresholdHr`, `betaBlocker`, `heartCondition`, `customZones` (`CustomZoneBoundary` — no in-app UI currently sets this), and `maxHrFormula` (defaults to `MaxHrFormula.tanaka`, `208 − 0.7 × age`). `isCautionMode` is a computed property, `true` when either `betaBlocker` or `heartCondition` is set.

`HealthProfileNotifier` (`lib/features/heart_rate/presentation/providers/health_profile_provider.dart`) is an `AsyncNotifier<HealthProfile>` that loads and saves the profile per active client via `healthProfileRepositoryProvider.getForClient()` / `.saveForClient()`, keyed off `activeClientProvider`. A one-time `_migrateLegacyProfileOnce()` step migrates the old single-profile SharedPreferences keys (`hr_age`, `hr_resting_hr`, `hr_measured_max_hr`, `hr_clinician_max_hr`, `hr_beta_blocker`, `hr_heart_condition`) into the "self" client row (`kSelfClientId`), guarded by the `health_profile_migrated_v1` flag.

=== Onboarding Flow

`_HealthProfileOnboarding` (`lib/features/heart_rate/presentation/widgets/health_profile_onboarding.dart`), launched via `showHealthProfileOnboarding()`, is a 4-step bottom sheet (`_step` 0–3: age; resting + measured max HR; medical flags; clinician cap) that writes each step's fields to `HealthProfileNotifier` via `_saveCurrentStep()`. Steps can be skipped (`_advance(skip: true)`). It's triggered automatically from `HeartRatePanelScreen._onFirstVisit()` when `profile.age == null`, and fires `HrAnalyticsEvent.onboardingCompleted` on completion.

`showDisclaimerIfNeeded()` (`lib/features/heart_rate/presentation/widgets/disclaimer_dialog.dart`) shows the first-use disclaimer once, gated on the `hr_disclaimer_shown` SharedPreferences flag.

[[zone-calculation]]
== Zone Calculation

`calculateZones()` (from `package:hr_zones`) selects the most personalised and safest applicable method, trying each in priority order and returning the first that has enough data:

[cols="1,2,1"]
|===
| Priority | Method | Reliability

| 1
| `ZoneMethod.custom` — `HealthProfile.customZones` is set (no in-app UI currently sets this)
| High

| 2
| `ZoneMethod.clinicianCap` — `HealthProfile.clinicianMaxHr` is set. Always wins over the fallback chain and stays High even in caution mode — the clinician's guidance is treated as authoritative.
| High

| 3
| `ZoneMethod.lthrFriel` — `HealthProfile.lactateThresholdHr` is set (no in-app UI currently sets this). Uses Joe Friel's published lactate-threshold-anchored 5-zone bands.
| High (Low in caution mode)

| 4
| `ZoneMethod.hrrKarvonen` — a max HR (measured or age-estimated) and `restingHr` are both available
| High if the max HR is measured, Medium if estimated (Low in caution mode)

| 5
| `ZoneMethod.percentOfMeasuredMax` — `measuredMaxHr` is set
| High (Low in caution mode)

| 6
| `ZoneMethod.percentOfEstimatedMax` — fallback using `maxHrFormula` when only age is available
| Medium (Low in caution mode)
|===

NOTE: Caution mode (`isCautionMode`) downgrades reliability to `ZoneReliability.low` for methods 3–6, but *not* for `custom` or `clinicianCap` — those two stay High regardless of caution flags, since they're authoritative external input rather than a derived estimate. Keep this distinction correct in any UI copy — it's user-visible safety messaging, and a blanket "caution mode is always Low reliability" claim is wrong for a user with a clinician cap set.

=== Five-Zone Model

[cols="1,1,1"]
|===
| Zone | % Range | Label

| 1
| 50–60 %
| Easy (Recovery)

| 2
| 60–70 %
| Light (Aerobic)

| 3
| 70–80 %
| Moderate (Aerobic)

| 4
| 80–90 %
| Hard (Anaerobic)

| 5
| 90–100 %
| Very Hard (VO₂ Max)
|===

Percentages are of the resolved `maxHr` for max-HR-based methods, of heart rate reserve (`maxHr − restingHr`, offset by `restingHr`) for `hrrKarvonen`, or of `lactateThresholdHr` for `lthrFriel` (whose top band extends to 110 % of LTHR).

=== ZoneConfiguration Output

`calculateZones()` returns a `ZoneConfiguration?` (`null` if no method has enough data) containing:

* `List<CalculatedZone>` — each zone with `lowerBound`, `upperBound`, `lowerPercent`, `upperPercent`, `label`, `effortLabel`, `descriptiveLabel`, `color`, and the computed `displayLabel` getter (`'$effortLabel ($descriptiveLabel)'`)
* `method` — the selected `ZoneMethod`
* `reliability` — `ZoneReliability.high` / `.medium` / `.low`
* `maxHr` — the anchor HR used for percentage calculations
* `reason` — human-readable explanation, surfaced as the `ReliabilityIndicator` tooltip

`zoneConfigurationProvider` (`lib/features/heart_rate/presentation/providers/zone_configuration_provider.dart`) derives this from `healthProfileProvider`.

== Charts

`HeartRateChart` (`lib/features/heart_rate/presentation/widgets/heart_rate_chart.dart`, `fl_chart`) renders the windowed and full-session heart rate traces. The BPM line is curved (`curveSmoothness: 0.15`, to reduce sensor spike flicker), plotted over optional zone-band background annotations (`rangeAnnotations`, toggled via `zoneBandsProvider`), with dashed per-zone threshold lines (`_thresholdLines`, `dashArray: [4, 4]`) each labelled with its percentage and BPM value. The X-axis uses adaptive `M:SS` labels (`_xInterval(totalSeconds)` sizes the tick interval to the session length). `_TrendChartSection` in `heart_rate_panel_screen.dart` shows a windowed `HeartRateChart` alongside a `SparklineWidget` full-session trace, falling back to a second `HeartRateChart` when fewer than 2 readings exist. The window duration (30/60/90/120/300 s, default 60 s) is persisted via `ChartWindowNotifier` (`lib/features/heart_rate/presentation/providers/chart_window_provider.dart`, key `hr_chart_window_seconds`).

=== Zone-Coloured Line

By default, the live hero trace and both the windowed and full-session charts colour the line — and the area beneath it — by training zone rather than a single colour. `zoneLineGradient(ZoneConfiguration config, {required double topBpm, required double bottomBpm, required Color belowZonesColour, double opacity = 1, bool fade = false})` (`lib/features/heart_rate/presentation/widgets/zone_line_gradient.dart`) is a pure function returning a vertical `LinearGradient` (`topCenter` → `bottomCenter`) with paired hard stops at each zone edge that falls within `[bottomBpm, topBpm]`; the rect it's painted over must have its top edge at `topBpm` and bottom edge at `bottomBpm` for the stops to land on the correct BPM. `opacity` scales every stop's colour; `fade` additionally ramps alpha to zero at the bottom, for use as a fill gradient. A reading below the lowest zone, or in a gap between custom zone bounds, is painted in a neutral grey (`belowZonesColour`) rather than a zone colour.

`SparklineWidget` (`lib/core/widgets/sparkline_widget.dart`) gained optional `lineGradient` and `fillGradient` parameters, painted over the whole widget with its top mapped to the data maximum and its bottom to the data minimum; when set, they replace the plain `lineColor` and faded `fillColor`. `HeartRatePanelScreen`'s private `_zoneTraceGradients` helper builds these from `zoneLineGradient` for the live hero trace and the full-session sparkline.

`HeartRateChart` gained a `zoneColouredLine` parameter (default `true`). Its line gradient uses `gradientArea: LineChartGradientArea.wholeChart` with top/bottom set to the chart's `maxY`/`minY`, so the gradient's hard stops line up with the dashed threshold lines. fl_chart paints the below-bar fill over a rect running from the highest plotted spot down to the chart floor, so the fill gradient is built from the max reading down to `minY`, at 0.1 opacity.

`zoneColouredLineProvider` (`lib/features/heart_rate/presentation/providers/zone_coloured_line_provider.dart`) is a `Notifier<bool>` mirroring `zoneBandsProvider`'s SharedPreferences-backed pattern — key `hr_zone_coloured_line`, default `true`, persisted on `toggle()`. `HeartRatePanelScreen` watches it and passes `zoneColouredLine` through to `HeartRateChart` and conditionally builds gradients for the two sparkline traces. Turning the toggle off, or having no `ZoneConfiguration` at all (no health profile), falls back to the previous single-colour behaviour for all three traces.

Tests render the traces and sample pixel colours via `PixelProbe` (`test/helpers/pixel_probe.dart`) so a dropped or misaligned gradient fails rather than passing silently.

NOTE: The saved cardio session's heart-rate chart on the workout detail screen is out of scope for this feature and still uses the theme's primary colour throughout — zone-colouring it would need the session owner's health profile rather than the active client's, and hasn't been implemented.

== Session Statistics

`_calculateStats()` in `HeartRatePanelScreen` derives average/min/max BPM from `HeartRatePanelState.readings`. Elapsed time is tracked in `HeartRatePanelController` via a wall-clock anchor (`_monitoringSince` / `_accumulated`) rather than a tick counter, so time spent backgrounded is still accounted for correctly on resume.

== Time-in-Zone Summary

`calculateTimeInZones()` (from `package:hr_zones`) processes the timestamped `HrReading` list against a `ZoneConfiguration` to produce per-zone `ZoneDuration`, `moderateOrHigherDuration` (zone 3 and above), and `recoveryHrDrop` (peak session BPM minus the BPM of a final reading at least 55 seconds after the previous one — `ReadingCadence.cooldownGap`). `_ZoneRow` in `heart_rate_panel_screen.dart` renders each zone's share as a proportional fill bar.

== Caution Mode

`CautionBadge` (`lib/features/heart_rate/presentation/widgets/caution_badge.dart`) renders when `profile.isCautionMode` is `true`:

* Copy is selected from `S.warningBetaBlocker` / `S.warningHeartCondition`, concatenated when both flags are set.
* Zone reliability follows the priority-chain rules above — Low unless a clinician cap is set, in which case it stays High.
* `HeartRateZoneLegend` (`lib/features/heart_rate/presentation/widgets/heart_rate_zones.dart`) shows `s.clinicianLimitsInUse` when `config.method == ZoneMethod.clinicianCap`.

== Reliability Indicator

`ReliabilityIndicator` (`lib/features/heart_rate/presentation/widgets/reliability_indicator.dart`) maps `ZoneReliability` to colour, icon, and label (green `Icons.verified` High, amber `Icons.info_outline` Medium, red `Icons.warning_outlined` Low), with `config.reason` as the tooltip.

== Symptom Reporting

`SymptomReportButton` (`lib/features/heart_rate/presentation/widgets/symptom_report_button.dart`, label `s.symptomReportButton` = "Report Symptom") renders while `panelState.isMonitoring` is `true`. `_showSymptomDialog` lists the four symptom strings; selecting one calls `_showStopExerciseDialog`, which calls `onStopRequested()` (`controller.stopMonitoring`) *before* the stop-exercise `AlertDialog` is shown, and fires `HrAnalyticsEvent.warningDisplayed` with `type: 'symptom_report'`.

== Max HR Alert

`MaxHrAlertNotifier` (`lib/features/heart_rate/presentation/providers/max_hr_alert_provider.dart`) holds `vibrationEnabled` / `soundEnabled` / `cooldownSeconds` (default 15 s), persisted via SharedPreferences (`hr_max_alert_*` keys). `HeartRatePanelScreen._checkMaxHrAlert()` fires `HapticFeedback.heavyImpact()` and/or plays `sounds/timer_complete.wav` when `panelState.currentHeartRate >= zoneConfig.maxHr`, throttled by the cooldown.

[[background-keep-alive]]
== Background Keep-Alive

On Android, `ForegroundKeepAlive` (`lib/core/foreground/foreground_keep_alive.dart`, provider `foregroundKeepAliveProvider`) reconciles the demands of the heart rate panel, cardio tracking, and coach mode into a single `ForegroundSessionService.update()` call, so the three features never fight over separate foreground notifications: `setCardio({sessionRunning, gpsEnabled, hrConnected})`, `setHeartRatePanel({monitoring, hrConnected})`, and `setCoach({required bool active})`. The service runs whenever cardio wants it running, the heart rate panel is monitoring with a connected strap, or the coach is active; only cardio ever requests GPS. `HeartRatePanelController._syncKeepAlive()` calls into it after start/stop/disconnect and on connection-state changes, as does `CardioTrackingController._syncForegroundService()` (see xref:features/cardio.adoc[Cardio Tracking]) and `coachKeepAliveProvider` (below). `ForegroundSessionService.update()` takes a `coachActive` parameter alongside the existing ones; `FlutterForegroundSessionService` adds the `mediaPlayback` foreground service type (`ForegroundServiceTypes.mediaPlayback`, requiring the `FOREGROUND_SERVICE_MEDIA_PLAYBACK` manifest permission) whenever the coach is active, and chooses the notification title and text accordingly: a cardio session with GPS on keeps the existing "RepFoundry is tracking your workout" / "Cardio session in progress", the heart-rate-only case reads "RepFoundry is monitoring your heart rate" / "Heart rate monitor connected", and the coach case (no GPS) reads "RepFoundry is tracking your workout" / "Your coach is with you". Only one notification is ever shown, even when more than one feature is demanding the service. While the coach is active the notification carries a *Turn coach off* button (`stopCoachButtonId`). Every `startService` passes `callback: foregroundTaskStart`, a `@pragma('vm:entry-point')` function that installs a `TaskHandler` in the service's isolate; its `onNotificationButtonPressed` relays the id with `FlutterForegroundTask.sendDataToMain`, which requires `FlutterForegroundTask.initCommunicationPort()` in `main()`. The service surfaces presses as `ForegroundSessionService.coachStopRequests`, passed through `ForegroundKeepAlive.coachStopRequests`; `coachKeepAliveProvider` answers with `setEnabled(false)` on the trainer settings, which silences the coach and releases the keep-alive. Verified on a Galaxy S9+ by sending the button's own broadcast intent. The test double is `FakeForegroundSessionService`; see `test/core/foreground/foreground_keep_alive_test.dart`.

Coach mode's own demand is computed by `coachNeedsBackgroundProvider` (`lib/features/trainer/presentation/providers/coach_keep_alive.dart`), which is `true` when the trainer entitlement is granted, the coach is enabled, the safety disclaimer has been accepted, `TrainerSettings.speakInBackground` is on, and `activeWorkoutControllerProvider` reports an active workout. `coachKeepAliveProvider` reports this to `ForegroundKeepAlive.setCoach()` via a container subscription (`ref.container.listen(..., fireImmediately: true)`) rather than `ref.listen` — a provider-internal listener on a derived provider is lazy, the same reason `CoachBridge`'s entitlement subscription uses the same pattern; a mutation test confirmed `ref.listen` misses every change case here. It is mounted in the router's `ShellRoute` alongside `coachBridgeProvider` and `hrEventSourceProvider`.

`TrainerSettings.speakInBackground` (default `true`, SharedPreferences key `trainer_speak_in_background`, setter `setSpeakInBackground`) is the user-facing *Speak in background* switch — see xref:ROOT:guide/trainer.adoc[] for the end-user description. With it off, `CoachBridge._onEvent` drops coaching events while `WidgetsBinding.instance.lifecycleState` is `hidden`, `paused`, or `detached` (`inactive` does not count, so a brief interruption like the notification shade doesn't silence the coach), and an `AppLifecycleListener(onHide:)` stops any speech already in progress. On iOS, `audio` was added to `UIBackgroundModes` in `ios/Runner/Info.plist` so the app is allowed to keep playing the coach's voice in the background at all (`flutter_tts` already uses the playback audio category with `duckOthers`/`mixWithOthers`); iOS still suspends the app between lines unless something else — such as an active Bluetooth heart rate connection — keeps waking it.

Tests: `test/features/trainer/presentation/coach_keep_alive_test.dart`, `test/app/coach_keep_alive_mount_test.dart` (mounts the real router), the "speak in background (#93)" group in `coach_bridge_test.dart`, and the extended cases in `test/core/foreground/foreground_keep_alive_test.dart`.

[[activity-nudges]]
== Activity Nudges (Coach)

`ActivityDetector` (`lib/features/trainer/application/activity_detector.dart`) is a pure-Dart, HR-stream-driven detector that invites the user to start logging a session once their heart rate has been elevated for a while without one running. `ActivityDetector({window = 90 s, episodeGap = 2 min})` exposes `onReading({elevated, at, sessionRunning}) → bool` and `onSignalLoss()`:

* An episode requires the elevated heart rate (Zone 2+) to be sustained continuously for the full 90-second window before it triggers; a single reading dropping below the elevated threshold resets the window.
* After a trigger, the detector needs a continuous 2-minute episode gap below the threshold before it will arm again, so it doesn't repeat-invite mid-session.
* A `sessionRunning: true` reading marks the episode as already under way rather than triggering, so finishing a workout out of breath doesn't earn an invitation.
* `onSignalLoss()` resets the window without counting as a completed invitation.

`HrEventSource._handleActivity()` (`lib/features/trainer/presentation/providers/hr_event_source.dart`) feeds the detector every heart rate reading: `elevated` is `zoneNumberFor(config, bpm) >= 2`; `sessionRunning` is `activeWorkoutControllerProvider.hasActiveWorkout || cardioTrackingProvider.isRunning`, each read guarded with `ref.exists` so neither controller is built as an unwanted side effect just to check it. The whole path is skipped unless `settings.enabled && disclaimerAccepted && activityNudgesEnabled` — entitlement gating itself is enforced separately, inside `TrainerEventBus.emit`. `_onSignalLoss()` calls `detector.onSignalLoss()`.

A trigger emits a new `TrainerEventKind.activityDetected` / `ActivityDetected` event. `CoachingEngine` routes it through `_speak(..., SpeechPriority.encouragement)`, so it passes through the same encouragement gate as other encouragement (blocked above the user's safe max heart rate, in caution mode, and in zone 5). `HrEventSource._offerBlocked()` applies the same three conditions before emitting at all, so the on-screen offer is withheld too; the episode still counts as offered. Three phrases per persona were added — `coachSteadyNudge1-3`, `coachHypeNudge1-3`, `coachSergeantNudge1-3` — wired through the ARB, `phraseResolvers`, and `persona_packs.dart`; `persona_packs_test.dart` now lists this kind in `_spokenKinds`.

`TrainerSettings.activityNudgesEnabled` (default `false`, SharedPreferences key `trainer_activity_nudges`, setter `setActivityNudges`) is the user-facing *Offer to join when you get moving* switch — see xref:ROOT:guide/trainer.adoc[] for the end-user description.

`ActivityNudgeListener` (`lib/features/trainer/presentation/widgets/activity_nudge_listener.dart`) wraps `ScaffoldWithNavBar` in the router's `ShellRoute`. It subscribes to the trainer event bus for `ActivityDetected` events and shows a `SnackBar` (10 s duration, `persist: false`) whose action button calls `activeWorkoutControllerProvider.notifier.startWorkout()` then `router.go('/workout')`. New ARB strings: `activityNudgeMessage`, `activityNudgeStart`, `trainerActivityNudges`, `trainerActivityNudgesSubtitle`.

Tests: `test/features/trainer/application/activity_detector_test.dart` (synthetic 1 Hz heart rate traces covering brief spikes, dips, breathers between sets, episode re-arming, active sessions, and signal loss), `test/features/trainer/application/coaching_engine_activity_test.dart`, `test/features/trainer/presentation/hr_event_source_activity_test.dart`, `test/features/trainer/presentation/widgets/activity_nudge_listener_test.dart`, and `test/app/coach_keep_alive_mount_test.dart` (mounts the real shell).

[[weekly-heart-report]]
== Weekly Heart Report

`lib/features/heart_rate/application/weekly_heart_report.dart` defines `HeartSessionKind` (`strength`, `cardio`), `HeartSessionSummary` (`workoutId`, `kind`, `title`, `startedAt`, `avgBpm`, `peakBpm`), and `WeeklyHeartReport` (`sessions`, `avgBpm`, `peakBpm`, `dailyPeakBpm` — 7 entries, oldest first — `secondsInZone` — `Map<int, int>`), with an `isEmpty` getter.

`BuildWeeklyHeartReportUseCase.execute({clientId, now, ZoneConfiguration? zones})` (`build_weekly_heart_report_use_case.dart`) reads `WorkoutRepository.getWorkoutHistory` for the last seven days and, per workout, takes `CardioSessionRepository.getHeartRateSamples` — converting zone seconds via `currentZoneFromConfig(bpm, zones)?.zoneNumber`, with the title resolved from `ExerciseRepository` — or falls back to the logged sets' `avgHeartRate`/`peakHeartRate` for a strength session. `buildWeeklyHeartReportUseCaseProvider` lives in `lib/core/providers.dart`; `weeklyHeartReportProvider` (`presentation/providers/weekly_heart_report_provider.dart`) is a `FutureProvider.autoDispose` watching `activeClientProvider` and `zoneConfigurationProvider`.

`WeeklyHeartReportScreen` (`presentation/screens/weekly_heart_report_screen.dart`) is routed as a nested `GoRoute(path: 'weekly-report')` under `/heart-rate` in `lib/app/router.dart`, giving the URL `/heart-rate/weekly-report`; `_WeeklyReportRow` pushes it via `context.push('/heart-rate/weekly-report')`. ARB strings are prefixed `weeklyHeartReport*`. Tests: `test/features/heart_rate/application/build_weekly_heart_report_use_case_test.dart` and `test/features/heart_rate/presentation/screens/weekly_heart_report_screen_test.dart`.

== Settings Integration

`SettingsScreen` includes a Health Profile section (`_Set2Card`) bound directly to `healthProfileProvider` / `userAgeProvider`: age, resting HR, measured max HR, beta-blocker toggle, heart-condition toggle, a read-only zone-method + reliability summary row, a link into the 4-step onboarding sheet (`s.setUpHeartRateZones`), a zone-colour-bands toggle bound to `zoneBandsProvider`, and a zone-coloured-line toggle bound to `zoneColouredLineProvider`. There is no direct Settings row for the clinician-provided maximum or lactate threshold. `clinicianMaxHr` can be set via the onboarding sheet's fourth step, or via the second entry point described below; `lactateThresholdHr` has no in-app UI at all.

A separate Max Heart Rate Alert section binds to `maxHrAlertProvider` (vibration toggle, sound toggle, cooldown dropdown: 10/15/30/60 s), followed by the general disclaimer paragraph (`s.warningGeneralDisclaimer`).

The clinician-provided maximum has a second entry point: `_HealthProfileForm` in `lib/features/clients/presentation/screens/client_detail_screen.dart` renders the full health-profile form (age, resting HR, measured max HR, clinician max HR, beta-blocker and heart-condition toggles) and saves it via `healthProfileRepositoryProvider.saveForClient()`. This is reachable for the self client too, not just coached clients — `ClientRepository.watchClients()` (`lib/features/clients/data/drift_client_repository.dart`) does not filter out `kSelfClientId`, and `client_roster_screen.dart` pushes `/clients/<id>` for every roster row including "Me". For a solo user who hasn't switched `activeClientProvider` away from the self client, this form and the Settings/onboarding paths above all read and write the same `HealthProfile` row.

However, `/clients` is *not* one of `ScaffoldWithNavBar._coreTabPrefixes` (`lib/core/widgets/scaffold_with_nav_bar.dart`) — the five routes (`/workout`, `/history`, `/cardio`, `/heart-rate`, `/settings`) that get the bottom navigation bar on a phone-width window. The only navigation to `/clients` is through `DesktopNavRail`, and `ResponsiveContext.hasNavRail` (`lib/core/responsive/breakpoints.dart`) only returns `true` once the window is at least `Breakpoints.tablet` (600 dp) wide — below that, `hasNavRail` is unconditionally `false`. So below the tablet breakpoint there is currently no route to the client detail screen, and by extension no phone-width path to this second entry point.

== Analytics Events

HR-related analytics events (`HrAnalyticsEvent`, `lib/features/heart_rate/domain/analytics_events.dart`) are fired through `HrAnalyticsReporter`. The MVP uses `NoopAnalyticsReporter` (debug log only); a production reporter can be swapped in via `hrAnalyticsReporterProvider`.

[cols="1,2"]
|===
| Event | When fired

| `onboardingCompleted`
| User finishes the 4-step onboarding sheet

| `healthFieldCompleted`
| User saves an optional health field

| `cautionModeActivated`
| A medical flag is set

| `zoneMethodSelected`
| `zoneConfigurationProvider` recalculates a non-null `ZoneConfiguration` — fires on every recalculation triggered by a health-profile change, not only when the selected method itself changes

| `customCapUsed`
| Clinician cap is entered

| `warningDisplayed`
| A warning or symptom dialog is shown
|===
