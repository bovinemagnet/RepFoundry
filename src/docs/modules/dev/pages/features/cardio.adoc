= Cardio Tracking
Paul Snow
0.0.0
:description: Guide to the cardio session tracking feature in RepFoundry.
:page-aliases: ROOT:features/cardio.adoc

The cardio tracking feature records duration-based activities — running, cycling, rowing, and similar exercises — with optional GPS distance, incline input, and live BLE heart rate monitoring.

== Overview

A cardio session is wrapped inside a standard `Workout` record so that it integrates with workout history, streaks, and analytics without a separate data model.
When the user saves a session, `SaveCardioSessionUseCase` creates the enclosing `Workout` retroactively with the recorded start and end time, then attaches a `CardioSession` record to it.

== CardioSession Model

[source,dart]
----
class CardioSession {
  final String id;                 // UUID v4
  final String workoutId;          // FK → Workout.id
  final String exerciseId;         // FK → Exercise.id
  final int durationSeconds;       // total active duration
  final double? distanceMeters;    // null when GPS unavailable or not tracked
  final double? incline;           // treadmill / machine incline in percent
  final int? avgHeartRate;         // BPM average for the session; null if no HR monitor
}
----

=== Derived Properties

[source,dart]
----
Duration get duration => Duration(seconds: durationSeconds);

// Returns null when distanceMeters is null or zero
double? get paceMinutesPerKm {
  if (distanceMeters == null || distanceMeters! <= 0) return null;
  final distanceKm = distanceMeters! / 1000;
  return (durationSeconds / 60) / distanceKm;
}
----

== Tracking Screen

`CardioTrackingScreen` renders a live dashboard driven by `CardioTrackingState` — elapsed time, GPS distance/pace, and current BPM are all fields on that state, updated by `CardioTrackingController` on a 1-second timer and on each GPS/HR stream event.

== GPS Distance Tracking

RepFoundry uses the `geolocator` package to stream GPS position fixes.
Distance is accumulated by summing the great-circle distance between successive fixes.

=== Location Service

`LocationService` (in `lib/features/cardio/data/location_service.dart`) wraps `geolocator` and exposes a position stream.
The service requests *While in Use* location permission on first launch.

[cols="1,2"]
|===
| Platform | Permission requested

| iOS
| `NSLocationWhenInUseUsageDescription`

| Android
| `ACCESS_FINE_LOCATION`
|===

Declined or later-revoked permission leaves `distanceMeters`/`paceMinutesPerKm` `null`; the save path has no dependency on GPS state.

== BLE Heart Rate Monitor

The cardio feature integrates live BLE heart rate streaming via the `HeartRateService` interface and `FlutterBlueHeartRateService` implementation.
This is the same BLE layer shared with the xref:features/heart-rate.adoc[Heart Rate Monitoring] panel — `FlutterBlueHeartRateService` is a singleton, so a device connected from one screen stays connected on the other.

=== Connection Flow

. Tap the *HR Monitor* button to open the device picker (`HrDevicePickerDialog`).
. `FlutterBlueHeartRateService.scanDevices` streams devices advertising service `0x180D` as they're discovered, so the picker renders the growing list mid-scan rather than waiting for it to finish — see xref:features/heart-rate.adoc#device-scanning[Device Scanning] for the stream API.
. On selection, the service connects and subscribes to HR Measurement characteristic `0x2A37`.
. Live BPM readings stream to `CardioTrackingController.heartRateStream`.

A connection doesn't have to start from this screen. `CardioTrackingController.build()` checks `HeartRateService.isConnected` and, if a monitor is already connected — typically from the heart rate panel — subscribes to its readings synchronously and returns `CardioTrackingState(hrConnected: true)` immediately. `_listenToConnectionState()` keeps watching afterwards: if the service later transitions to `connected` from another screen it subscribes then too, and on `disconnected` it cancels the readings subscription and clears the connection state. `connectHeartRate` is now just `connectToDevice` followed by that same subscribe step. After a successful save, the controller re-adopts the existing connection rather than resetting to disconnected, so the strap stays connected for the next session or for the heart rate panel.

=== Connection State

`HrConnectionState` (`connected` / `reconnecting` / `disconnected`) drives `CardioTrackingState.hrConnected` / `hrReconnecting`, which the tracking screen renders as the connecting/connected/disconnected card states.

*Auto-reconnect:* `FlutterBlueHeartRateService._attemptReconnect` hands off to `ReconnectStrategy`, which on unexpected disconnection retries with exponential backoff — `defaultDelays` is `[2, 4, 8, 16, 32, 60, 60, 60]` seconds, so it keeps trying for a little over four minutes before giving up and emitting `HrConnectionState.disconnected`. The initial `connectToDevice` call is separately wrapped in `retryOnceOnFailure`, a single one-off retry after 1 second to absorb Android's transient GATT error 133 on first connect. Intentional disconnects (via `disconnect()`, which sets `_intentionalDisconnect`) bypass reconnection entirely.

=== Setup Help

`HrSetupGuideDialog` renders the device-specific pairing steps for Apple Watch, Samsung Galaxy Watch, and chest straps (sourced from the `appleWatchStep*` / `samsungWatchStep*` / `chestStrapStep*` ARB entries), opened via `showHrSetupGuide()`.

=== Foreground Keep-Alive

`CardioTrackingController._syncForegroundService()` does not call `ForegroundSessionService` directly — it goes through `ForegroundKeepAlive`, which reconciles cardio's demand for the foreground notification with the heart rate panel's, so the two features share one notification instead of fighting over it. See xref:features/heart-rate.adoc#background-keep-alive[Background Keep-Alive].

== Save Flow

`CardioTrackingController.save()`:

. Calls `SaveCardioSessionUseCase.execute()` with the accumulated metrics.
. A `Workout` is created retroactively with the session's `startedAt` and `completedAt` timestamps.
. A `CardioSession` is attached to the workout via its `workoutId`.
. State resets to `CardioTrackingState(savedSuccessfully: true)`; the screen clears its input fields and shows a snackbar. There is no navigation away from the Cardio tab.

[source,dart]
----
// Simplified save flow
final workout = await workoutRepo.createWorkout(
  startedAt: sessionStart,
  completedAt: sessionEnd,
);

final session = CardioSession.create(
  workoutId: workout.id,
  exerciseId: selectedExercise.id,
  durationSeconds: elapsed.inSeconds,
  distanceMeters: accumulatedDistance,
  incline: inclineValue,
  avgHeartRate: computedAvgBpm,
);

await cardioRepo.saveSession(session);
----

== Recordings and export

Alongside the `CardioSession` summary, RepFoundry persists the raw GPS track and heart-rate stream captured while the session was running, so a session can be reviewed and exported after the fact.

=== Domain models

[source,dart]
----
class CardioTrackPoint {
  final String id;                 // UUID v4
  final String cardioSessionId;    // FK → CardioSession.id
  final double latitude;
  final double longitude;
  final double? altitudeMeters;
  final DateTime recordedAt;
}

class CardioHeartRateSample {
  final String id;                 // UUID v4
  final String cardioSessionId;    // FK → CardioSession.id
  final int bpm;
  final DateTime recordedAt;
}
----

=== Storage

Two Drift tables back these models, added in schema v14 (migration step guarded by `from < 14`): `cardio_track_points` and `cardio_heart_rate_samples`, each keyed by UUID and foreign-keyed to `cardio_sessions`. See xref:database.adoc[Database] for the full column reference.

`CardioSessionRepository` exposes them independently of the session itself:

[source,dart]
----
Future<void> saveTrackPoints(String cardioSessionId, List<CardioTrackPoint> points);
Future<List<CardioTrackPoint>> getTrackPoints(String cardioSessionId);

Future<void> saveHeartRateSamples(String cardioSessionId, List<CardioHeartRateSample> samples);
Future<List<CardioHeartRateSample>> getHeartRateSamples(String cardioSessionId);
----

=== Capture

`CardioTrackingController` accumulates a `CardioTrackPoint` for every position the GPS stream emits while the session is running. Heart-rate samples are not captured from the live BPM stream directly — at save time, the controller reads the session's start/end window from `hrSessionRecorderProvider`, which has been recording every BPM reading from the connected monitor independently (shared with the heart rate panel), and turns the readings in that window into `CardioHeartRateSample` records.

Both lists are passed through `SaveCardioSessionInput.trackPoints` and `SaveCardioSessionInput.heartRateSamples` into `SaveCardioSessionUseCase.execute()`, which persists them via the repository methods above alongside the `CardioSession` itself. A session saved with GPS off, or with no heart rate monitor connected, simply has an empty list for the corresponding recording.

=== Export

`CardioSessionExporter` (`lib/features/cardio/application/cardio_session_exporter.dart`) is a pure function module with no Flutter or platform dependencies — it builds a GPX 1.1 document from a list of `CardioTrackPoint`s and a `timestamp,bpm` CSV (ISO-8601 UTC timestamps) from a list of `CardioHeartRateSample`s, which keeps both builders trivially unit-testable.

`CardioSessionExport`, exposed via `cardioSessionExportProvider`, loads a session's recordings, runs them through `CardioSessionExporter`, and hands the resulting files to `shareFilesProvider` (`lib/core/share/share_files_provider.dart`) to invoke the platform share sheet. `shareFilesProvider` is overridable in widget tests so the share sheet itself is never exercised. File names are passed separately as `fileNameOverrides` rather than relying on the `XFile`'s own name, because `XFile.fromData` drops its name on web.

Only recordings that are non-empty are exported; when both are empty, `_CardioCard` on the workout detail screen (`ROOT` History → workout detail) disables its *Export* action rather than sharing empty files. Sessions saved before schema v14 have no rows in either table, so they behave the same way — Export stays disabled.

NOTE: These recordings are included in the full JSON export/import (`ExportDataUseCase` / `ImportDataUseCase`) but are **not** part of the sync snapshot — `SyncSnapshot` carries the `CardioSession` summary only. See xref:features/sync.adoc[Cloud sync internals].

== Cardio history and progress

The History screen's *Cardio* tab is `CardioHistoryView` (`lib/features/history/presentation/widgets/cardio_history_view.dart`), a `History | Progress` segmented view over the active client's saved sessions, filtered by sport.

=== Providers

Four providers in `lib/features/history/presentation/providers/cardio_history_provider.dart` drive it:

[source,dart]
----
final cardioHistoryProvider =
    FutureProvider.autoDispose<List<CardioHistoryEntry>>(...);

final cardioSportFilterProvider =
    NotifierProvider<CardioSportFilter, String?>(CardioSportFilter.new);

final filteredCardioHistoryProvider =
    FutureProvider.autoDispose<List<CardioHistoryEntry>>(...);

final cardioProgressProvider =
    FutureProvider.autoDispose<CardioProgress>(...);
----

`cardioHistoryProvider` loads every session for the active client via `BuildCardioHistoryUseCase`. `cardioSportFilterProvider` holds the selected sport chip (`null` for *All sports*). `filteredCardioHistoryProvider` applies that filter and feeds both the History and Progress segments; `cardioProgressProvider` derives `CardioProgress` from the filtered list.

=== Building entries

`BuildCardioHistoryUseCase` and its output `CardioHistoryEntry` live in `lib/features/cardio/application/`. The use case reads every `CardioSession` for the client from `CardioSessionRepository`, resolves each one's enclosing `Workout` (for `startedAt`) and its exercise name from `ExerciseRepository`, and returns the results newest first. A session whose workout can no longer be found is skipped.

=== Progress computation

`CardioProgress.compute()` is a pure function — no clock, no repository — that reduces a list of `CardioHistoryEntry` over the last `weeks` calendar weeks (Monday-based, local time) into total distance, session count, total duration, a `weeklyDistanceKm` bucket per week, best pace, average heart rate, and a `paceTrend` of one `PacePoint` per session with a distance. Week boundaries are computed from calendar date components (`DateTime.utc(year, month, day)` differences), not raw `Duration` division, so a daylight-saving transition can't shift a session into the wrong week's bucket.

=== Route sketch

`CardioRouteSketch` and its `projectTrack()` function (`lib/features/history/presentation/widgets/cardio_route_sketch.dart`) draw the session's recorded `CardioTrackPoint`s as a line, with start and end markers, on a plain background — no map tiles. `projectTrack()` scales longitude by `cos(latitude)` of the track's mean latitude so the route isn't squashed east–west, then fits the result to the widget's bounds on its longer axis and centres it on the other.

=== Heart-rate trace

`_HeartRateTrace`, a private widget in `workout_detail_screen.dart` alongside `_CardioCard`, renders the session's `CardioHeartRateSample`s as an fl_chart `LineChart`, with the peak BPM called out above the chart. Both the route sketch and the heart-rate trace only render when the corresponding recording is non-empty.
