Implementation reference for cross-device sync. For what sync does from a user's
point of view — turning it on, what platforms it works between, and how conflicts
are resolved — see xref:ROOT:guide/sync.adoc[].

== Overview

The sync feature sits on top of the offline-first SQLite core.
All data is written locally first; sync runs after the fact (e.g. after completing a workout).
If the device is offline or sync fails, the user is unaffected.

Platform backends:

* *iOS* — CloudKit via a platform channel (`com.repfoundry.app/cloudkit_sync`)
* *Android* — Google Drive hidden app data folder (`driveAppdataScope`) via `googleapis` + `google_sign_in`

Platform selection is handled by `SyncServiceFactory`: `Platform.isIOS` returns `CloudKitSyncService`, `Platform.isAndroid` returns `GoogleDriveSyncService`, and unsupported platforms return `NoopCloudSyncService`.

== SyncOrchestrator — 6-Step Flow

`SyncOrchestrator.sync()` coordinates the full sync cycle.
A `_isSyncing` guard prevents concurrent runs.

. *Check connectivity* — query `connectivity_plus`; bail with error status if offline
. *Create local snapshot* — build a `SyncSnapshot` via `SyncSnapshotSerialiser.createFromDatabase()`, including soft-deleted rows. Client-scoped tables — workouts, sets (via their parent workout), cardio sessions, personal records, body metrics, and stretching sessions (via their parent workout) — are read for the Me client (`kSelfClientId`) only; workout templates and programmes are not client-scoped and are read in full
. *Download remote snapshot* — call `CloudSyncService.downloadSnapshot()`; returns `null` on first sync
. *Merge* — pass local and remote snapshots to `SyncMergeEngine.merge()`; if no remote exists, use local as-is
. *Upload merged snapshot to cloud* — `CloudSyncService.uploadSnapshot()` serialises the merged snapshot as JSON
. *Apply merged snapshot to local DB* — `SyncSnapshotSerialiser.applyToDatabase()` writes all entities in a single Drift batch/transaction using a guarded upsert. On conflict a row is only overwritten when the incoming row would also win under `SyncMergeEngine`'s own rule — a tombstone beats a live row, a later tombstone beats an earlier one, and between two live rows the strictly newer `updated_at` wins, with ties keeping the existing local row

The upload happens before the local apply step. If the cloud upload fails, local state is left unchanged relative to the pre-sync database and a later retry can merge again from a fresh snapshot.

The client-scoping in step 2 exists because the snapshot carries no client roster and no per-row owner field, and `applyToDatabase()` gives every new row it writes the Me client on the receiving device — including another client's rows would silently re-own them as Me's once applied elsewhere. The guarded upsert in step 6 mirrors `SyncMergeEngine`'s conflict rule so a slow upload can't let an edit made mid-sync get reverted by a merge that was computed before it happened.

`CloudSyncService.isSupported` is `false` for `NoopCloudSyncService` (see below) — the implementation used on desktop and web platforms with no real cloud backend. `SyncOrchestrator.sync()` checks this before doing any work and returns an error result immediately rather than attempting an upload that would be silently discarded. `SyncOrchestrator.deleteCloudData()` waits for any in-flight `sync()` call to finish before deleting the cloud copy, so a sync that's already mid-flight can't upload and recreate the data the user just asked to delete.

== SyncMergeEngine — Conflict Resolution

The merge engine uses a tombstone-aware *updatedAt-wins* strategy, resolved per entity by UUID:

* Entities unique to either side are included unconditionally
* If either side is soft-deleted, the tombstone wins so deletes are not resurrected
* If both sides are soft-deleted, the later `deletedAt` wins
* If neither side is soft-deleted, the entity with the newer `updatedAt` wins
* Ties (equal timestamps) favour the local copy
* Output snapshot carries `snapshotAt: DateTime.now().toUtc()` and inherits `deviceId` and `schemaVersion` from the local snapshot

The merge is a pure function with no side effects — it takes two `SyncSnapshot` objects and returns a third.

== CloudSyncService Interface

`CloudSyncService` (`lib/features/sync/domain/sync_service.dart`) defines four methods:

[cols="2,3",options="header"]
|===
| Method | Description

| `Future<bool> isAvailable()`
| Check authentication and service availability

| `Future<void> uploadSnapshot(String jsonData, {bool interactive = false})`
| Upload serialised snapshot JSON to cloud. `interactive` is true only for explicit Settings actions.

| `Future<String?> downloadSnapshot({bool interactive = false})`
| Download latest snapshot; returns `null` if none exists. `interactive` is true only for explicit Settings actions.

| `Future<void> deleteCloudData({bool interactive = false})`
| Delete cloud data and sign out
|===

=== CloudKit Implementation (iOS)

`CloudKitSyncService` communicates via a platform channel named `com.repfoundry.app/cloudkit_sync`.
Method calls map directly to the interface: `isAvailable`, `uploadSnapshot`, `downloadSnapshot`, `deleteCloudData`.
`PlatformException` on `isAvailable` gracefully returns `false`.

=== Google Drive Implementation (Android)

`GoogleDriveSyncService` uses `googleapis/drive/v3` with `google_sign_in`.
Data is stored as `repfoundry_sync.json` in the hidden `appDataFolder` space (not visible in the user's Drive).
Upload updates the existing file by ID if found, otherwise creates a new file.
`deleteCloudData()` deletes the file and calls `_googleSignIn.disconnect()`.

Drive authentication is split by caller:

* Manual Settings actions use `interactive: true` and can show Google sign-in / scope authorization UI.
* Automatic app-resume and post-workout sync use `interactive: false`; they only use cached lightweight authentication and fail quietly if auth is unavailable.
* HTTP authorization headers are read per Drive request so expired access tokens are refreshed by the sign-in client instead of reusing stale headers.

== State Management

Two Riverpod providers manage sync state, both defined in `lib/features/sync/presentation/providers/sync_settings_provider.dart`.

=== SyncSettings (persisted)

`syncSettingsProvider` — `NotifierProvider<SyncSettingsNotifier, SyncSettings>`

Persisted via `SharedPreferences` under keys: `cloud_sync_enabled`, `cloud_sync_last_sync_at`, `cloud_sync_device_id`, `cloud_sync_consent_given`.

[cols="1,1,2",options="header"]
|===
| Field | Type | Description

| `enabled` | `bool` | Whether sync is turned on
| `lastSyncAt` | `DateTime?` | Timestamp of last successful sync
| `deviceId` | `String` | UUID v4, generated on first build and persisted
| `consentGiven` | `bool` | Whether user has accepted the sync consent dialog
|===

=== SyncState (in-memory)

`syncStateProvider` — `NotifierProvider<SyncStateNotifier, SyncState>`

Not persisted; resets to `idle` on app restart.

`SyncStatus` enum: `idle`, `syncing`, `success`, `error`.

=== Consent Flow

A `SyncConsentDialog` is shown the first time sync is enabled.
The dialog returns a `bool`; setup only proceeds if consent is granted.
After consent, Settings runs an interactive first sync. `cloud_sync_enabled` is persisted only after that first sync succeeds, which prevents later automatic sync attempts from silently failing before cloud authentication is established.
